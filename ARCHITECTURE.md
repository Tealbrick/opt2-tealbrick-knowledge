# Knowledge (Tealbrick mini app): architecture

State: verified against the repo on 2026-10-17. Claims cite paths in this repo. Anything not verified is marked UNVERIFIED. For the whole system see the system `ARCHITECTURE.md` and `SYSTEM-OVERVIEW.md`.

## Common app pattern (verified for this repo on 2026-10-17)

- **Runtime**: Node 24, TypeScript run through `tsc` to `dist/`, UI built by `scripts/build-ui.ts` (no bundler; content-hashed `assets-<hash>/`). The app is started by `startApp` from `@opt2-tealbrick/miniapp-sdk` (`src/main.ts`).
- **Dockerfile**: two stages on `node:24-slim` pinned by digest, `pnpm install --frozen-lockfile --ignore-scripts`, `pnpm run build && pnpm prune --prod`, the manifest also copied to `/opt/tb/tealbrick.manifest.json` (the `tb-exec` default), `USER node`, no `VOLUME`. The SDK drops root to uid 1000 itself when the platform starts the container as root (Railway volumes are root-owned).
- **Data**: one SQLite file `TB_DATA_DIR/app.db` owned by the SDK. App tables use their own prefix; SDK tables use `tb_*`. On Railway there is ONE volume per service: the backup directory is `<data mount>/backup`, so the volume size is data plus backup (C28).
- **Migrations**: `migrations/NNNN_name.sql` (or `.ts` exporting `up(db)`). The SDK enforces forward-only: gap-free from 0001, one transaction each, sha256 recorded in `tb_migrations`. A changed, missing, misnamed or `down` migration stops the app with `migration_invalid`.
- **Backups and restore**: SDK cron runner writes `tb-backup-<UTC>.tar.gz`; export `tealbrick.export/1` never carries the instance key, KEK, keys, secrets or sessions. Restore at next boot with `TB_RESTORE_FROM`.
- **Authorization**: the bridge gates (`gate()`); the SDK decides (`authorize()`): run, hold or refuse. Holds and receipts live in the app's own `tb_receipts` table. Raw call input is never stored, only a digest.
- **Manifest** `tealbrick.manifest.json` is the only source for operations, scopes, settings, hooks, companions, skills, runtime hints, backups and UI paths. Schema `tealbrick.miniapp/2`, `sdkMajor 1`, `source.license Apache-2.0`. Agent ops become MCP tools `<product>__<op>`. Person ops are owner UI only.
- **Generated**: `gen/` (openapi, kit, docs, railway) is produced by `tb-gen` and is not committed. The typed client kit is built into `dist/kit` and imported as `#kit` in apps that have one.
- **Standard UI pages** (from the kit `AppShell`): Holds, Receipts, Agents and scopes, Keys (where the app has keys), Backups and export.
- **Licence files**: `LICENSE` (Apache-2.0), `NOTICE`, `THIRD_PARTY_NOTICES.md`. The brand mark and app art are Tealbrick artwork and are not Apache-licensed.
- **Private by design**: no public address. Only the bridge is public.

## Knowledge: what it does

Knowledge is a normalization wrapper over engines. Canonical documents stay in Knowledge (engine independent) and are projected into GBrain pages; the engine can be rebuilt from Knowledge (`afterRestore` requeues everything). Engine tools are exposed 1:1 under a dynamic `engine` list, bounded by a pinned surface, and anything else fails closed. Without an engine, recall degrades to keyword search (`degraded: true`).

## Operations (from `tealbrick.manifest.json`)

66 operations (verified 2026-11-06, C392 R2 and R1 hardening).
- Hot (agent, C336 M4): `recall` (meaning), `search` (words), `get` (open a `ref`), `context` (size-capped block for hooks), `ask` (engine think, model cost), `remember` (`text` or `items[]` with `source`, deduped per area). Every recall/search hit carries `ref` and `source` (citation; migration 0002 adds `source_ref`, `source_url`, `content_digest`).
- Read (agent, per area): `recall`, `areas_list`, `collections_list`, `collection_get`, `collection_tree`, `documents_search`, `document_get`, `document_revisions`, `comments_list`, `links_list`, research reads, `engine` (dynamic, search mode since 0.1.26: agents see `knowledge__engine_search` / `knowledge__engine_call` instead of ~100 `gb_*` tools; ceiling destructive).
- Write (agent): `remember`, `collection_create`, `document_create`, `document_update`, `comment_add`, `link_add`, `research_source_add`, `research_chat_start`, `research_ask`.
- Destructive, hold `destructive`: `document_delete`, `collection_delete`, `link_delete`, `research_source_delete`.
- Person: 10 library reads, 4 writes, 4 destructive (held).
- Relationships (C392 R1): agent `relationships_list`, `relationship_get`, `relationship_propose` (write, idempotency required, receipt); person `relationships_overview`, `relationship_confirm`, `relationship_set` (see "Relationships" below). Narrowing policy: the three agent ops `unsupported` (R1 hardening F6), the three person ops `none`.
- Forget a person (C392 R2): person `relationship_forget_scan` (read) and `relationship_forget` (destructive, hold `destructive`, idempotency required, receipt). Narrowing policy `unsupported` for both (see "Forget a person" below).
- Rules' `rules.narrowing` memory tags are consumed (`src/narrowing.ts`). Writes to existing items obey read visibility (F90, C150). URL research sources are deferred until a network policy exists (C61). There is no attachment storage.

## Scopes, hooks and companions

- **App callers (C373):** Observer writes through `areas_list`, `document_create`, `document_update` (`APP_CALLER_OPS`); any other op from an app is `scope_denied`. An app sees and writes only `kind: shared` areas. Its write right is the SDK `own` default row of its instance (the SDK 0.1.41 default grants give an app only `read` on the shared area; spec and manifest need two disjoint `shared` entries to fix this cleanly). The owner switches it off with `tb.scopes_set` on that row. `kn_state` key `caller/<ins>` keeps the display name. Tags are stored as sent (lower-case, at most 20, 40 characters each); Knowledge derives none.
- **Scopes:** `area` (access `read`, `contribute` = read, create, update, `read_write`). Default grants: own area read_write, shared area read. The shared company area is read for every connected agent; write is off until the owner turns it on per agent (C1). Events `agentAdded` (creates the company area and that agent's area) and `keysChanged`.
- **Person and team memory (C373):** areas `person-<24 hex>` (a Governance person) and `team-<24 hex>` (a Governance team) are NOT SDK scope instances; Knowledge decides them per call from its copy of the Governance directory (`src/people.ts`, `src/area-access.ts`) on top of the bridge edge grant, the SDK rows above and Rules narrowing. An agent owned by person P: read and write on P's area (its default write area), read on the areas of teams it or P is in, read on another person Q's area only through an owner grant "team T may read Q" (`kn_team_grants`, optionally tag-limited; a tag-limited area is readable only by item-filtering ops). No directory or no owner = own agent area + company only (fail closed). Scope functions return `null` for these ids, so the SDK gate checks the caller's best area row. The owner manages grants on the Access page.
- **Hooks:** None.
- **Companion grants it asks for:** `fleet` `directory_feed` (read): the Governance directory (contract `fleet.directory_feed/1`, vendored in `src/contracts/`, provenance in `test/contracts/PROVENANCE.md`), read by `src/directory-feed.ts` at start, every 60 s, after `agentAdded` and from the Access page; never inside an agent call. Governance 0.3.0 or newer serves it to Knowledge; an older one answers `no_access` and Knowledge keeps today's access. Before C373 no grant was asked. It calls GBrain at `/mcp` (stateless JSON-RPC POST, no redirects, 2 MB response cap) and Open Notebook REST (4 MB cap).

## Relationships (C392 R1)

`src/relationships.ts` (store) and `src/relationship-ops.ts` (handlers). Agents keep, per OPERATOR (a Governance directory person who owns agents), a record of each third-party person: identities, a relationship type, the owner's stance and trust, and cited history.

- **Operator:** for an agent op, the agent's owner in the directory copy (`agentView`, the local copy only). No copy or no owner → 409 `relationships_unavailable` (fail closed). The agent input names no operator, so an agent never reaches another operator's people; such a person answers 404 `person_unknown`. Person ops name the `operator`; writes need it listed in the current copy (`directory_unavailable` / `person_unknown`, like `setGrant`). The overview reads what is stored without a copy.
- **Agents propose, the owner confirms:** type, identity and label proposals are `pending` until `relationship_confirm`. The type that reads back is the confirmed type (`unknown` until then); a pending type shows as `proposedType`. A new third party gets a person row (its label and the identities it was seen with) with type `unknown` and trust `hold`; an identity another of the operator's people already has is 409 `identity_taken`. History items (`contact`, `promise`, `topic`, text ≤ 500) are observations, written at once, each with a citation {source, ref, at}.
- **Owner only:** stance {tone, formality, avoidTopics} and trust (`reply`, `draft_only`, `hold`; default `hold`) are set only by `relationship_set` (a person op). The agent input schemas have no such field (`additionalProperties: false`), and the `kn_rel_proposals.field` CHECK allows only type, identity and label. An inferred value never raises an agent's permission.
- **Identities:** `normalizeHandle` (`@opt2-tealbrick/manifest`) for email, slack (person ids U/W only), buzz and telegram; phone = `+` and 6 to 15 digits; other = trimmed. Unique per (operator, kind, value); two operators may each know the same identity.
- **Audit:** every write appends to `kn_rel_log` (UPDATE and DELETE abort). Log rows and receipts carry ids, field names and enum values only, never identity values, labels, stance text or history text.
- **Trust only on a verified sender (R1 hardening F5, release blocker):** trust is keyed on WHO SENT a message, and an email From address is easy to fake. `kn_rel_identities.verified_by` (migration 0006): `platform_id` = a Slack, Buzz or Telegram id whose link to the person the OWNER confirmed (an accepted identity proposal, or `relationship_set` `verifyIdentities`); NULL = unverified (every email, phone and other identity, and every identity an agent put in, platform ids included). `dkim_spf_aligned` is reserved for an email sender that Connect attests per message (spec follow-up messages/1 `author.verified`); no code path writes it, the CHECK allows it only on email and `platform_id` only on slack/buzz/telegram, and the hook `senderVerification` (src/relationships.ts) answers null for any email until that attestation is passed and checked there. Outputs keep the owner's `trust` and add `effectiveTrust` + `trustBasis` (`effectiveTrust` in src/relationships.ts): stored `hold` → `hold`; looked up BY IDENTITY (relationship_get `identity`, the sender of a message) → the stored trust when that identity is verified, else at most `draft_only`; looked up BY PERSON ID (relationship_get `person`, relationships_list, the overview, relationship_set) → no sender is named, so the stored trust is capped at `draft_only` when the person has no verified identity; with one, the stored trust reads back and `trustBasis` says it holds only for a message from a verified identity. An agent answering a message must look the person up by the sender identity (skill, op descriptions). Knowledge only answers: the SENDING side (the agent runtime, Connect) enforces `effectiveTrust`; Knowledge sends nothing. Email cannot be verified by anyone in this release (`identity_unverifiable`).
- **Untrusted wrapper (R1 hardening F4, release blocker):** every text an agent or a third party supplied reads back only under `observed: {untrusted: true, …}` (the platform marker for third-party content, specs MANIFEST.md "untrusted" / SDK-API.md §emit): per person the agent's label, identity values (with `verifiedBy`) and the pending `proposedType`; per history item the text and citation; per proposal the value and citation. Owner-set fields stay outside: `type`, `trust`, `effectiveTrust`, `trustBasis`, `stance` and `label` when the owner typed it (`kn_rel_people.label_set_by`, migration 0006, backfilled from `kn_rel_log`; null outside = the label is an agent's). An ACCEPTED label proposal stays an agent's words (`observed.label`); `relationship_set label` (also with the same text) makes it the owner's. Ids, counts, enum kinds, `proposedBy` (the verified caller id) and times stay outside. The R2 forget scan/confirmation (owner-only display text, document titles from the Library) is not wrapped.
- **Caps and checks (R1 hardening):** an identity whose stored JSON {kind, value} exceeds 400 characters (the proposal value CHECK) is `invalid_identity` (F1); an identity proposal that another person of the operator already has is `identity_taken` at propose time, and `relationship_confirm` reports an accepted identity that became taken in `conflicts` (it stays pending; the other decisions apply; an unknown or decided id still refuses the whole call) (F3); at most 50 pending proposals per person (`too_many_pending`, 409) (F3); each history item may carry its own citation, else the call's; a citation `at` more than 5 minutes after the server clock is `invalid_input` (F7); a person keeps at most 500 history rows: over that, the oldest contacts and closed promises are dropped (never this call's rows; `pruned` in the answer, a `history_pruned` log row with counts) and when only topics and open promises remain the write is refused `history_full` (no commitment is dropped silently) (F8); `new` must be an object (F9).
- **Stale directory window (F10):** the operator comes from the local Governance directory copy (read at start, every 60 s, after `agentAdded` and from the Access page). When Governance cannot be read (transient errors), the last good copy keeps deciding for up to 10 minutes after that read (`MAX_STALE_MS`, src/directory-feed.ts); a refusal drops it at once. So an owner change in Governance reaches Relationships within about a minute, but up to 10 minutes late while Governance is unreachable: in that window an agent still reads and proposes for its OLD owner's people (and a removed agent still reads them). After it every agent op fails closed (`relationships_unavailable`).
- **Known limits:** the sensitive-category ban (health, religion, politics, sexuality) is a skill rule plus the fixed enums: the server has no category field and does not scan history text (a shared detector word list does not exist yet, SCOPE-V2 Q7). No owner page yet (R1-UI). No merge, no team sharing (R1b), no Observer evidence feed (R3).

## Forget a person (C392 R2)

`src/forget.ts` (store and queue) and two person ops in `src/relationship-ops.ts`. The Relationships person record is the anchor: its label and identity values are the search terms. Owner (person caller) only; an agent or app is `scope_denied`, and the skill tells agents to send the owner to the Relationships page.

- **Operator check:** the operator must have stored people or be listed in the directory copy (a forget must still work for an operator who left Governance). Another operator's person is 404 `person_unknown`.
- **Scan** (`relationship_forget_scan`, read, changes nothing; and inside every forget): every document of every area, live and soft-deleted: title (`title`), current body, summary, tags and source fields (`body`), every stored revision (`revision`, so a name that is only in an old version is found) and every comment (`comment`). Terms: the label and each identity value (a phone also without `+`), lower-cased, case-insensitive substring (JavaScript `toLowerCase`, so non-ASCII letters fold too); terms shorter than 4 characters are skipped. The scan answer names the document id, area, `deleted`, the places and the document's current title (cut to 120 characters, so the owner can tell a false match apart), never body or comment text; at most 500 (`truncated`). The forget's own report (the SDK stores it, sealed, for an idempotent replay), receipts, `kn_rel_log` and `kn_forget_queue` carry ids and counts only, never a title or the label.
- **Confirmation (S2):** `relationship_forget_scan` with the planned `purgeDocuments` also returns `confirmation`: plain text that names the person (label, id, operator), says the delete is permanent, lists each document to delete (area, title, id; "already deleted in the Library" when soft-deleted), the ids that would be kept, how many other documents stay, and every `notPossibleYet` line. `relationship_forget` has a `holdView` with the same text (the handler spec gets the input only, so it reads the bound database; unbound → ids and the warning) and a hold summary (`redact` without output) with ids and counts. Finding: SDK 0.1.48 never holds a person op (`handlePersonOp` runs it at once; holds exist only for agent-audience calls, ops.js `audience_not_agent`), so today the hold view is not shown; the owner page must show `confirmation` and ask before it calls the forget (R1-UI). A real-SDK test (`test/forget-real.test.ts`) proves the person call answers 200 at once and that a retried forget with the same idempotency key answers the stored report (the handler does not run again).
- **Forget** (`relationship_forget`, one transaction): the scan, then a hard delete of the person's identities, edge, proposals and history and the person row (explicit deletes; the composite foreign keys cascade too), then ONE tombstone row in `kn_rel_log` (`person_forgotten`: actor, operator, person id, time, counts only). Older `kn_rel_log` rows of the person carry ids, field names and enum values only (checked: `person_created` detail = identity KINDS, `proposed` = field + proposal id, `relationship_set` = field names and type/trust enums), so the log keeps no identity value or label. `purgeDocuments` (ids from a scan) are hard-deleted only when THIS call's scan matched them (any other id is `refused`, nothing of it deleted): the document row (FTS row by trigger, then an FTS `optimize` merge so no delete marker keeps a term), every revision, comment, link (both ways) and projection row; its children move up to its parent.
- **Engine page:** a purged document of an engine deployment is queued in `kn_forget_queue` (migration 0005, ids only) in the same transaction. The op then purges at most 10 pages at once (`INLINE_PURGE_LIMIT`; each helper call can take up to 25 s; the rest stay queued and are reported `engine_pending`) through the GBrain helper path `/purge-page` (`services/gbrain/helper.ts`: `gbrain delete knowledge-docs/<doc> --source-id <ka-…> --purge --force --request-id <uuid> --json`, upstream's trusted local CLI; only `knowledge-docs/kdoc_<ULID>` pages of `ka-<24 hex>` sources). A helper failure leaves the row queued (`engine_pending` in the report); the projection timer drains it with the projection backoff (at most 1 h, never gives up). No purge runs while a projection pass runs (that pass could still write the page). Agents still can never purge (`guard.ts` refuses `purge` unchanged). The helper reads `page_not_found` from the CLI's `--json` envelope (`code`, else `error.code`, last JSON line; upstream src/cli/cli-error.ts:53-74), never by substring; any other error keeps the row for a retry. The helper listens on 127.0.0.1 only; the one way in is tb-exec's helper proxy, which needs a valid instance assertion and a declared path (SDK tests: `opt2-tealbrick-sdk` packages/miniapp-sdk/test/exec/tb-exec.test.ts, "helper proxy refuses a wrong key, a sibling service, a tampered body, a missing header and a replay" and "helper proxy refuses an undeclared path even with a valid assertion"). `/purge-page` is declared only on the `gbrain` service.
- **Report:** `deleted.relationships` counts, `documents` {matched, purged (engine `purged`/`pending`/`none`), pending, refused} and `notPossibleYet` in every scan and forget answer: Foundry (no dataset delete until F2), LCM-X (local store; forget hides rows, purge per session), backups (the last `retain` scheduled backups from the manifest `backups` section, plus pre-update snapshots), research sources (not scanned in R2; `research_source_delete`), GBrain pages not projected from a Knowledge document, GBrain purge tombstones, other people's Relationships rows, deleted rows in free database pages and write-ahead logs.

### GBrain purge semantics (pinned upstream 36121271, 0.60.424.0)

Read with `git show 36121271caf3dea8ffc2240deb28c5da50f7eade:<path>` (paths at that commit):

- **MCP cannot purge.** `delete_page` (src/core/ops/pages.ts:418-446) calls `assertPurgeParams` (src/core/persistence/purge-params.ts:15-20): `purge: true` from any caller with `remote !== false` is `permission_denied` "purge is only available to the local CLI". So the app's MCP client can only soft-delete; the purge runs through the helper on the engine host. `purge_deleted_pages` (pages.ts:477-496) is admin, local-only and brain-wide; it is not used.
- **No automatic purge here.** Soft-deleted pages are hard-deleted by the autopilot/dream `purge` phase after 72 h (src/core/cycle.ts:1748-1766, src/core/sync-reconcile.ts:59-75); this deployment runs `gbrain serve` only, so a soft-deleted page (every ordinary `document_delete`) stays in the engine until purged.
- **What `delete <slug> --purge` removes** (`purgePageInTransaction`, src/core/persistence/page-purge.ts:269-362; summary page-purge.ts:1-16 and `PURGE_RESIDUALS` :63-66): the page row; page versions (`page_versions.page_id` ON DELETE CASCADE, src/schema.sql:668); chunks with their embeddings and search vectors (`content_chunks.page_id` CASCADE, schema.sql:343); timeline entries (`timeline_entries.page_id` / `event_page_id` CASCADE, schema.sql:634, :645); links, tags and raw data (cascade); facts filed on the page (explicit `DELETE FROM facts WHERE source_id AND source_markdown_slug`, page-purge.ts:315, since `facts` has no foreign key to pages); takes, take proposals, open loops, aliases, file rows and the query cache (page-purge.ts:299-332). It works on a live page and on a soft-deleted tombstone (src/core/persistence/page-prepare.ts:500).
- **What stays:** text-free tombstones: `page_purges` (source, slug, content hashes of the page and every version; blocks re-import of the same content, page-purge.ts:229-266), `fact_purges` (fact hash and the entity slug, which can name the person, page-purge.ts:233-235) and `take_purges`; the purge mirror `.gbrain/purge-events.jsonl` (slug and hashes); facts about the person filed on OTHER pages (for example from agent `remember`, not projected from a Knowledge document); and, per upstream, backups, provider copies of embeddings, and deleted rows in database pages and the write-ahead log until vacuum. These are in `notPossibleYet`.

## Settings, keys and environment

Settings (all `mutable:false`, set at deploy): `engine` (gbrain; hindsight is disabled), `research` (default false), `model_provider` (openai default, google, anthropic). Model roles (C373, `settings.modelRoles`): `embeddings` and `reasoning`, both `required:false`, `minPolicy:standard`, `usedBy:["gbrain"]`. `tb-exec` fills the bound role into the `gbrain` service as `KN_EMBEDDINGS_*` and `KN_REASONING_*`. `services/gbrain/models.ts` plans each boot: a role binding, else the legacy `model_provider` defaults when their key is in env, else no model. A fresh brain starts with `init --embedding-model …` or `--no-embedding`. A built brain keeps the model it was built with: a different binding is reported as `embeddings_changed` and is not applied (re-index is not automatic yet). The wrapper writes labels only to `knowledge-models.json` and answers them at helper path `/models`; the app reads them strictly (`readEngineModels`) and raises attention `model_role_optional` or `embeddings_changed`. Legacy keys, from the bridge key store (account default): `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`; they are optional fallbacks and do not hold the engine. Env passed to the app: `KNOWLEDGE_ENGINE`, `KNOWLEDGE_RESEARCH`, `KNOWLEDGE_MODEL_PROVIDER`, `KNOWLEDGE_GBRAIN_URL`, `KNOWLEDGE_GBRAIN_ADMIN_TOKEN`, `KNOWLEDGE_NOTEBOOK_URL`, `KNOWLEDGE_NOTEBOOK_PASSWORD` (wired by the deploy recipe). Service knobs: `KNOWLEDGE_MIGRATION_{WAIT_S,LOCK_STALE_S,POLL_S,RETRY_MIN_S,RETRY_MAX_S}`. Default model names live in `src/config.ts` and must become customer-editable (C186, open). The Dockerfile does not set `TB_DATA_DIR` or `TB_BACKUP_DIR`; the deploy recipe sets them (SDK-API section 13; `tb-gen railway` sets both).

Companion services (built from `services/<id>/Dockerfile`, started with the SDK `tb-exec` wrapper, which fetches declared keys and runs backup dump and restore): `gbrain-db` (pgvector on Postgres 17), `gbrain` (upstream commit pinned, a Tealbrick boot wrapper with a crash-safe migration lock and a helper), and, when research is on, `notebook-db` (SurrealDB under the Business Source License 1.1, C155) and `notebook` (Open Notebook). ## External calls and background work

- **External:** Only the engines, on the private network. Model providers (OpenAI, Google, Anthropic) are called by GBrain and Open Notebook, not by the app code.
- **Background:** Projection outbox drain every 30 s (batch 20, max 12 attempts, backoff 5 s up to 1 hour). Engine probe at start and every 10 minutes (feeds SDK `attention()`). Retry of failed rows at boot. Migrations on the engine services are crash-safe (C69).

## Person UI

Memory (Library, Recall, Memory status), Research, Access (C373: people, teams, grants), Holds, Receipts, Agents and scopes, Keys, Backups and export (`src/ui/main.tsx`).

## Requirements and runtime hints

A model for the embeddings role and one for the reasoning role (both optional; without them recall is keyword-only and ask is unavailable). The legacy provider keys still work as a fallback (OpenAI by default; Anthropic mode still needs an OpenAI key for embeddings). Engine and database services must be healthy for engine-backed ops. SurrealDB is BSL 1.1: self-hosting inside Knowledge on the customer's Railway is expected to be fine, but legal confirmation is open (C155).

App port 5310, 0.5 cpu, 768 MB, data 5 GB plus backup 20 GB. Engine only: about 2.0 cpu, 3.3 GB RAM, 37 GB volume. With research: about 3.5 cpu, 5.4 GB RAM, 47 GB (computed from the manifest; UNVERIFIED against a deployed template). Backup cron `23 2 * * *`, retain 14; each service with a dump is dumped by `tb-exec`.

## Known gaps

- Stable 0.1.20 pins SDK 0.1.22; the dev build already pins 0.1.25.
- Model names are set by the model roles (C373); the legacy defaults in `src/config.ts` stay only as a fallback.
- Changing the embeddings model of a built index needs a re-index; it is reported (`embeddings_changed`), not applied.
- No service Dockerfile sets `USER` and no manifest service sets `dropPrivileges`, so the four service images run as their upstream image's default user (root-capable).
